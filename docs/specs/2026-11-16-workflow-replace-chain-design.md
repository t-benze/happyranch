## 2. Run states, exception recovery and wake contract

Use the hold definition in msg230, confirmed by Founder msg231 (msg229 is the dispatch record), as written:

> A run is in exactly one of three states:
> - **Running:** one of its step tasks is in progress.
> - **Held:** no step task is in progress, the run hasn't finished, and the engine can't choose the next step from the definition by itself.
> - **Finished:** completed, failed or cancelled.
>
> What causes a hold:
> - the step task failed or timed out without a result, or failed or timed out after a result
> - its result can't be accepted (wrong shape, too large, an outcome the definition doesn't list)
> - the assigned agent is unavailable or no longer eligible
> - the step's revision limit is used up
>
> What happens on a hold: the engine wakes the initiator with the cause and the step. The initiator then retries the step, re-briefs it, swaps that step's agent, or cancels the run. Until then the engine creates nothing.

Store business state as `running | held | finished`, with nullable terminal outcome `completed | failed | cancelled` only for Finished. Keep internal progress separately: `queued | executing | result_pending_settlement | cancelling`. A running run has one selected outstanding step; a held run has a held node cursor and zero outstanding step tasks; a finished run has neither. A held cursor may identify a never-launched node (unavailable assignee). Old stopped visit rows remain immutable history, never “in progress.” A scheduler wait is not an inability to choose a next step. Unknown native execution remains an outstanding step until safe closure; absence of a PID is insufficient. This is the explicit operational interpretation in assumption 6, subject to sign-off.

A valid result follows a declared edge: next node, bounded correction edge, hold, explicit fail, or terminal. Shape/size/outcome/native failure holds cannot be silently reclassified as success, nor produce a synthetic result. A definition fail edge finishes failed and wakes the initiator; retry within a finished run is refused. No automatic retry follows a hold. An agent-declared BLOCK mapped to a hold also wakes the initiator. Coding merge uncertainty is an agent-reported hold cause, not a workflow merge state.

### Durable wake payload

One committed event produces one durable obligation addressed to the recorded initiator task **and permanent agent ID**, not its parent, a team manager inferred later, a thread, or the founder. Proposed bounded canonical payload, `workflow-sequential-initiator-wake@2`, at most 16 KiB:

```json
{
  "format": "workflow-sequential-initiator-wake@2",
  "notification_id": "server-generated",
  "run_id": "server-generated",
  "event_id": "server-generated",
  "event_sequence": 7,
  "initiator_task_id": "TASK-source",
  "initiator_agent_id": "engineering_manager",
  "kind": "held",
  "state": "held",
  "terminal_outcome": null,
  "node_id": "review",
  "role_id": "reviewer",
  "visit_id": "last-stopped-visit-or-null",
  "step_task_id": "TASK-step-or-null",
  "result_id": null,
  "cause": "task_timed_out_without_result",
  "diagnostic": "bounded sanitized cause",
  "assignment_generation": 1,
  "remaining": {"visits": 10, "recoveries": 1, "node_revisions": 0},
  "actions": ["cancel"],
  "action_refusals": {"retry": "revision_limit_exhausted"},
  "selected_output_refs": [],
  "effect_disposition": "unverified"
}
```

This is illustrative, not a client-supplied authority record. `kind` is `held | failed | returned | cancellation_finished`; a failure observed before native closure may publish `failure_observed` with state Running, no replacement action and an explicit unsettled reason. The Held obligation follows closure. Return includes terminal outcome and selected bounded output references, not all output bodies. Cause enums cover the four hold categories plus explicit agent hold, unavailable current authority, and uncertainty. Raw provider text/credentials/private input bodies are excluded. Only addressed outputs are disclosed under current authority. Wake references do not establish remote truth or permission.

A wake is written in the same transaction as the hold/terminal event. Queue publication is post-COMMIT and replayable. Inbox acceptance is durable, indexed by `(initiator_task_id, notification_id)`; queue insertion alone is not delivery acknowledgement. The next genuinely admitted initiator session receives a bounded page of unconsumed events plus stable cursors for additional pages, under existing prompt-size limits. Once its genuine INTEGER result commits, its decision receipt atomically records the consumed notification IDs. A crash before that result leaves events pending for a new genuine session. A crash after result consumption replays that decision's effects, never re-invokes them. Duplicate queue delivery can at most cause a no-op claim, not a duplicate logical continuation.

### Generic callback and result acceptance

For new visits, `workflow-sequential-callback@2` is a canonical UTF8 JSON STRING in the genuine completion summary with exactly `format`, bounded `outcome`, `content_base64` and `findings`. Remove `capability_claims`; no trusted domain-check receipts are composed. The daemon derives run/visit/task/principal/SID/INTEGER result identities from the actual committed native row. The node declares either generic canonical JSON-object content (48 KiB) or immutable UTF8 document content (1 MiB). Envelope metadata/findings retain finite original bounds. The engine validates that declared generic representation, size, selected recipient/provenance and native settlement; it does not interpret keys such as repository/head/PR/merge. Outcome names are bounded tokens declared by the definition, not a global Coding vocabulary. A next/terminal edge requires the node's declared output; a declared hold may carry empty content with causal findings. A malformed or unknown outcome holds, creates no output/successor and retains only bounded causal native evidence. Historical callback@1 and its capability receipts are unchanged.

### Closed initiator vocabulary

Keep `workflow_start` for initiation; do **not** overload start to mean recovery. Add closed `workflow_control` and `workflow_wait` decisions. No manager prose is interpreted as a command. `workflow_control` requires `format=workflow-sequential-control@2`, run ID, stable operation key, expected run CAS, and `expected_held_event_id` (a required nullable field; omission is invalid), with exactly one action below. This new @2 shape leaves historical cancellation bytes unchanged.

At the round-2 source pin, existing cancellation takes run CAS without a held-event field (`runtime/workflows/sequential_engine.py:603–608`); its writer handles both active and held runs and retained cancellation replay (`runtime/workflows/sequential_cancel.py:179–197`). The following is the proposed @2 contract, owned by S4a with native cancellation delivery in S6b, not a claim that these controls already exist.

| Action | Allowed fields and observable effect |
| --- | --- |
| `retry` | Reason; optional per-step model/effort edit. New visit/task for the same held node and selected input snapshot, carrying original assignment unless explicitly edited. No old task revival. |
| `rebrief` | Reason and a bounded replacement step supplement, optional model/effort. Replaces only that node's initiator supplement for this attempt; immutable definition responsibilities and original request remain separately visible. Fresh visit/task, original and new brief digests retained. |
| `reassign` | Reason, permanent target agent ID, optional replacement supplement and model/effort. Revalidate eligibility/independence and current target executor, then create a fresh visit/task for the held node. Does not rewrite the role's run default or other visits. |
| `cancel` | Reason. Fence new work and use native cancellation ownership/settlement; no replacement. May be requested while Running. |

For a **fresh operation**, apply this state-by-action table under the same writer/CAS boundary. The CAS field is required in every variant; where an action is allowed it must equal the current run CAS. A current held event means the event establishing this still-current Held cursor, never an earlier hold after recovery.

| Observed state | Action | Expected run CAS | `expected_held_event_id` | Result |
| --- | --- | --- | --- | --- |
| Running, including never-held or resumed after a hold | `retry`, `rebrief`, `reassign` | Required | Must be null | Refuse `run_not_held`; no allocation. A previous hold ID cannot authorize running-step replacement. |
| Running, including never-held or resumed after a hold | `cancel` | Required; must equal current CAS | Must be null | Fence/drain the current outstanding step; no held event is invented. |
| Held | `retry`, `rebrief`, `reassign` | Required; must equal current CAS | Must equal current held-event ID (nonnull) | Apply only with the settlement, eligibility and original-limit conditions below. |
| Held | `cancel` | Required; must equal current CAS | Must equal current held-event ID (nonnull) | Fence the held cursor; no replacement step. |
| Finished | Any action | Required; cannot authorize a fresh effect | Must be null | Refuse `run_finished`; inspect the retained outcome. |

Running's internal `cancelling` substatus permits only replay of the already committed cancellation; a fresh key refuses `control_in_progress` and cannot request native cancellation twice. Null during Held, a missing field, a past/noncurrent event, or a nonnull event during Running/Finished refuses without effect. Validate the closed shape, then authenticate the immutable operation identity and check committed replay **before** current-state/CAS/event preconditions: an exact Held retry replay after it made the run Running returns its original IDs with its original nonnull held event. A cancellation replay after Finished similarly retains its original bytes. Same key/different bytes conflicts. A new operation after a later hold must use that new event and CAS.

Competing retry/rebrief/reassign/cancel operations against one Held event have one CAS winner; the loser records no control event, task, counter spend or cancellation effect. Running cancel racing step settlement likewise either wins the fence before advancement or refuses the changed CAS; it never silently converts its null event into a newly Held event or cancels a successor under stale authority. Refresh is explicit; transport uncertainty is not retry authority.

Retry/rebrief/reassign require Held, no in-progress task, positive original native/outer settlement where a task launched, current initiator task/session authority, and remaining original limits. Rebrief cannot change repository authorization or widen the goal. Reassign does not grant tools or repository access. Unknown external effects must be stated in the replacement brief; Coding roles must not repeat an uncertain merge. The generic engine does not decide whether a Git effect occurred.

Control processing is owned by the same genuine completion-result consumer as start: source task + actual session + immutable INTEGER result + canonical decision bytes. `(run_id, operation_key)` is unique; exact replay returns the original event/new-task IDs even after later run transitions. Same key/different bytes conflicts. Stale CAS or held-event ID produces a precise no-effect refusal and refresh guidance; no automatic rebase/resubmit. Validation failure consumes no task or revision budget, but ordinary bounded authoring-feedback limits still apply. Explicit idempotency records must survive restart; do not derive identity from an orchestration-step audit ID.

For @2 workflow decisions, add a common `consume_notifications` array of at most 32 server-issued IDs delivered to this actual session; it is optional/empty when no workflow events were presented. `workflow_start` and `workflow_control` accept it as part of their closed decision shape; `workflow_wait` requires it or an outstanding dependency. The server authenticates those IDs against the session's durable delivery snapshot and owned task, and atomically consumes them only with that genuine result's decision receipt. It never trusts an arbitrary client event ID. Existing ordinary `done`/delegate/escalate decisions consume their actually delivered event page through the same server-owned receipt without adding keys to historical decision bytes. More than one page remains pending and schedules the next continuation; no silent truncation or lost event is an acknowledgement.

`workflow_wait` means “I consumed these events; keep this source task delegated while the named outstanding runs/ordinary children continue.” It contains only known owned run IDs and consumed notification IDs. It cannot create, resume, fail or finish a run. After a returned/failed/cancelled run wake, the initiator may inspect its wider goal and issue another `workflow_start`, use existing delegation, wait, or eventually `done`/`escalate` under its ordinary contract. A `done` decision refuses while any owned run or ordinary child remains outstanding; it cannot abandon work implicitly.

### Revision and audit rules

Replace hard-coded two-return interpretation for new definitions with per-node declared revision/attempt limits and a total run visit bound. Recommendation: keep 64 total visits, 4096 events, 32 nodes, 16 roles; per-node revisions/attempts/recoveries at most 63/64/64, further intersected with original definition, settings, requested lower limits, root remaining allowances and existing org revise/retry policy. Pilot Coding can still default to two corrections; two is no longer an engine-wide product rule. Final numeric limits need sign-off and sizing evidence.

An automatic correction consumes its declared revision counter and a visit. A held-step replacement consumes an attempt/recovery and a visit; it cannot reset an exhausted revision counter. Changing model, agent, brief, key, task number or session creates no allowance. When a limit is exhausted, the wake shows the actual remaining values and why retry/rebrief/reassign are unavailable; cancel remains supported. New runs must account for the same wider-goal spent allowances. Automatic graph cycles remain bounded; no resume edge may jump to an arbitrary node or edit the graph.

The authoritative audit is the append-only workflow event stream, extended with `held`, `control_applied`, `finished`, `initiator_wake_created`, `initiator_wake_consumed` or equivalent normalized rows. It records before/after CAS, causal native result or terminal observation ID/digest (nullable result only when genuinely absent), actor task/agent/SID, command digest, assignment generation, before/after counters, replaced visit and fresh visit. A notification/consumption table may reference the event rather than duplicate its bytes. Human-readable `audit_log` entries use the **existing actual task ID and actor**; no new `audit_log.task_id` prefix or overloaded-field meaning. Task creation's existing conditional model-selection audit remains as THR-356 defines it. Event history is the replay authority; a log line is not.

### Cancellation and initiator loss

Cancellation wins by serialized CAS: after the fence no fresh acceptance, output selection, replacement or successor task may commit. An already committed original result may replay unchanged and drain native ownership without advancing. Cancelling one run leaves sibling runs and the initiator alive. Cancelling the initiator/ordinary ancestor fences **all** owned active runs and uses existing mixed cancellation/native owner paths. Never cancel siblings by enumerating only a current visit snapshot; membership is re-read under the cancellation writer. Missing/unknown handles and remote effects remain unknown after business cancellation.

If the initiating task becomes failed/cancelled/superseded, do not revive it and do not wake another manager implicitly. Fence its runs; drain/cancel them under their actual owners; retain undeliverable inbox rows with disposition `initiator_terminal`. Its ordinary parent observes the source's native failure through existing task handling. If its agent is unavailable but the source task is nonterminal, retain the addressed wake pending with a visible unavailable reason; no replacement agent is inferred. Root Pause delays new admission/launch/wake sessions under existing policy, while preserving committed obligations and native closure; Resume does not renew limits. No new thread/founder message is emitted by this mechanism.

## 4. Multi-run lifecycle and coexistence with chains

The source task remains native `in_progress` with `block_kind=delegated` while it owns outstanding work and has no active manager session. A workflow carrier remains a structural subtask, one per run, with no host execution. Native visit tasks stay children of that carrier. Replace singleton source ownership with a durable source wait-set ID and normalized membership linking source task, run, source result and start key. A source result may initiate several runs; many result rows from later sessions may initiate further runs on the same source task. Never stuff multiple run IDs into `tasks.note`, `active_chain`, `active_fanout` or `blocked_on_job_ids`.

The source has exactly one ordinary native execution owner at a time. Waiting on workflows is a dependency relation, not a new permission/native host owner. Preserve native creation marks and ownership-family union checks. For @1 history, `seq_source_waiting` still denotes its original single-run record. For @2, a stable source wait-set identity resolves indexed memberships; dispatch recognizes an initiator-continuation session as the ordinary owner with workflow dependencies. A sequential visit cannot execute manager decisions or start competing chains for its own node.

Admission sequence: authenticate a genuine source result → validate all batch commands → allocate immutable runs/carriers/first visits + membership + start events/outbox under one writer → park the source → positively settle the original source host/outer owner → publish each first step. A source batch's **one** native settlement proof releases each of its runs idempotently. It must not call singleton `selected_owner` and release just the first matching run. Failed/uncertain source outer settlement releases none and records an initiator-visible cause after safe handling; it is never inferred from callback HTTP200.

An initiator may be woken for A Held while B still executes. Its continuation sees A's wake, B's state and the remaining ordinary dependency summary. It may recover A, start C or wait. All wake arrivals coalesce into a single task queue claim while preserving individual event identities; events arriving during a live manager session remain pending for its next session. Returning A cannot mark source completed or unblock its ordinary parent while B runs. Run closure completes only A's carrier, appends A's inbox event, and wakes the source itself. Root `done` remains the only normal completion of its wider goal.

Chain/fanout coexistence is transitional, without retiring them:

- Existing ordinary chain/fanout carriers continue using their exact result/verdict/newest-leg and all-children barrier rules. Do not count workflow carriers as ordinary chain legs or fail an ordinary fanout because a workflow is Held.
- A source task may have ordinary dependencies and run memberships. The ordinary join checks only its ordinary dependency set; a central initiator readiness predicate combines that join with pending workflow inbox events. A hold or individual return is an event wake even when other dependencies are running. A routine join is not permission to issue `done` while a run remains outstanding.
- Starts from an eligible manager decision can coexist with earlier outstanding work, but one result contains one decision kind: a new start batch or a control or ordinary delegation, never implicit mixed side effects. A later workflow wake provides the next session in which the manager can start more work. A dormant source without pending events is not busy-polled to create additional runs.
- If an initiator has an active fanout while handling a workflow event, do not clear its fanout state at manager entry. Preserve it until its real join; similarly preserve active chain state. Event context and join context are separately attributed. A workflow-control decision does not advance/cancel an unrelated chain.

Concrete integration: extend closed `NextStep` parsing/serialization in `runtime/models.py`; route these decisions before ordinary v2 dispatch spending in `run_step._consume_completion_report` (currently line 2805), bound to immutable result-row identity. Put workflow bookkeeping in a new workflow-owned continuation owner, with a small orchestrator bridge; do not expand run_step into another engine. `_enqueue_parent_if_waiting` delegates workflow carrier events to that bridge and otherwise retains existing behavior.
