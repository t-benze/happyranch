## Curation comes before Ready

**EXISTING IDENTITY FEASIBLE: ordinary daemon-dispatched task to the retired source’s still-active, authorized former executable team manager, consuming a daemon-supplied read-only snapshot and returning curated items through its existing completion output.**

This is a source-supported feasibility verdict, not an executed curation result or permission grant. The agent does not open another agent’s workspace or Claude directory. The Founder’s confirmed Distill authorizes the daemon to collect the declared source corpus and supply it as task data to the selected existing processor. The daemon validates and publishes the result. Source identity, processing identity and eventual recipient identity remain separate. Instill does not have to exist when Distill starts.

### What curation must produce

Distill must select useful durable knowledge and label it **before** publication. An archive item is not eligible merely because a source note exists. One item per note is an allowed storage shape, not proof of curation. The processor must account for every source entry/file in the declared snapshot, retaining a disposition and reason even when it produces no selectable item.

| Content | Curation rule | Required attribution / qualification |
| --- | --- | --- |
| Durable facts and lessons | Select reusable findings and lessons supported by the source; exclude incidental chatter and unsupported conclusions. | Qualified source MEM/file references, source dates and observation cutoff; identify historical or uncertain statements. |
| Procedures | Select actionable, reusable procedures within their recorded scope; retain prerequisites and limits. | Source references and applicable dates; a procedure never supplies present execution permission. |
| Founder decisions and preferences | Select only when attributable evidence supports the human Founder origin; distinguish a decision from an agent’s interpretation or recommendation. | Cite the recorded Founder ruling/thread reference where available; otherwise label “source reports a Founder preference; attribution unverified,” without upgrading it to a directive. Current known rulings prevail. |
| Open work | Preserve useful references, not assignments. | Observed owner, status/date, next action and holds, with unknowns explicit; a fresh recipient must check current state. |
| Superseded, evicted, stale or promoted material | Inventory and retain reference-only context with a reason; do not revive stale bodies or copy shared KB bodies. | Original lifecycle, supersession/promoted-pointer reference and dates; ineligible for Instill. |
| Conflicting or uncertain material | Retain supported useful material with visible uncertainty/conflict warnings; withhold selection where attribution/body/safety cannot be established. | Identify the conflicting references and what is unknown. No claim of exhaustive conflict detection. |
| Excluded content | Exclude credentials, generated instructions/permissions, skills, identity/session/cache state, unrelated private content and unrestricted task/conversation histories. | Record category/reason and counts or explicit unknowns without exposing excluded secrets in diagnostics. |

The daemon checks that references resolve within the captured corpus or explicitly permitted cited provenance, every inventory entry has a disposition, IDs are unique, source/lifecycle restrictions are respected, and required attribution and dates are present or explicitly unknown. Structurally valid output alone does not prove good judgment; the S6 journey must inspect representative content for useful selection and honest attribution. The validator must not invent supporting evidence or treat model assertions as verified Founder authorship.

A verified empty corpus can yield an explicitly empty Ready archive. An actual curation failure cannot be disguised as “all items excluded” or an empty success. Malformed, incomplete, truncated, unsupported or missing processing output fails the attempt. No archive becomes Ready while required curation or required-source processing is unfinished. No UI may say “all knowledge captured.”

### Assumptions and Confusion Protocol

- **A1 — routing:** the former active executable manager is the proposed initial processor. Confirm its current charter permits the supplied curation task at S2 admission; never infer rights from former authority over the source. For an org without that manager, require an explicitly authorized existing owner or fail visibly. This is an implementation assumption, not a new Founder ruling or a new UI selector.
- **A2 — input:** Founder-confirmed source capture may be delivered as bounded task data under existing task visibility. It must not expose a corpus to an agent whose current charter forbids receiving it. If that requires a new data-access entitlement, stop for the Founder; do not rely on shared OS-user access.
- **A3 — capacity:** the complete declared snapshot and structured result fit supported task input/output limits. Use the existing task-input/attachment facilities only if already authorized and sufficient; do not truncate, silently sample, create a chunk-processing engine or ingest unrestricted history. An oversized corpus fails with an actionable reason; needed architecture beyond the PRD returns to the Founder.
- **A4 — execution:** the selected processor can follow its normal completion contract with curated content in its completion output (and the existing `done` decision for a task-owning root). The daemon waits for successful terminal execution and validated complete output, not just callback arrival. Ordinary launch/callback failures retain their authentic cause and uncertainty; no fake task/result/session is created.
- **A5 — data versus instruction:** the snapshot is explicitly quoted untrusted source material. The processor must not obey inherited instructions, execute procedures, browse unrelated records, alter source/recipient memory or publish KB entries. Its current charter remains authoritative; this is task scoping, not a claim of a new security sandbox.

If an assumption fails, preserve evidence and the prior Ready archive, mark the affected attempt Failed or retain an uncertain in-flight operation as appropriate, and return the concrete ambiguity to TASK-15170. Do not silently choose between conflicting contracts. New identity/permissions, destructive schema, architecture beyond the PRD, an estimate above 26 person-days or more than three code-defect REQUEST_CHANGES rounds per slice require the root’s Founder escalation. In-scope documentation corrections continue normally.

## S2 — Archive and Distill lifecycle

Founder confirmation creates one durable Distill operation bound to the source ID, cutoff, selected existing processor and exact declared coverage. Preserve the original operation after a lost response; reopening checks its state before another submission. Do not automatically create duplicate attempts. Record the actual processor/task/session/result references when available, without impersonating the source.

| State | Observable condition |
| --- | --- |
| Queued | Admitted operation persisted; processing has not started. |
| Processing | Source capture/curation/publication in progress; show actual phase, last update and operation ID, without invented percentages. |
| Ready | Entire declared corpus accounted for; curated items and manifest validated and durably published together. A verified empty corpus is visibly empty with zero eligible items. |
| Failed | Required read, curation, validation or publication failed with actionable cause. No selectable partial archive. Preserve failure and original operation identity. |

Each successful run creates one immutable archive ID/version identifying that capture. Retrying a confirmed Failed Distill is a new attempt/archive ID, with a new version reference; it never mutates earlier Ready payloads or hides failure history. Pending or uncertain work must be reopened and reconciled before a new attempt. A failed or newer pending run leaves all prior Ready versions selectable. Durable payloads/manifests live in org-owned storage independent of provider folders, task output scratch and job lifetime. No automatic archive deletion and no edit/delete/version-management UI. The manifest records org/archive/version/operation IDs, source permanent ID and captured name/team/provider, observation cutoff, processing date/owner, category counts or unknowns, exclusions/errors and item inventory. Each item has a stable archive-local item ID, qualified original references/dates, original authorship, eligibility and uncertainty/conflict/supersession flags. Closing a drawer does not cancel processing; omit cancellation unless a supported safe path exists.

Use additive feature-owned org tables reached from the schema owner `runtime/infrastructure/db/schema.py` **after** the fresh-schema `executescript` block (`:1575` through `:2230`). Keep the shared Database interface thin and feature operations in their owner. Proposed logical records, with final SQL reviewed in S2/S3:

| Record / proposed table | Required durable contents and constraints |
| --- | --- |
| `knowledge_distill_operations` | Org/source/operation IDs, fixed confirmation, state/phase, processor/task/result references, cutoff, timestamps and failure/uncertainty cause. Submission identity returns the same operation. |
| `knowledge_archives` | Unique archive ID and capture/version; originating operation and source ID; immutable manifest and curated item payload, coverage/dispositions, dates and processing ownership. Publish availability only with the complete validated payload. |
| `knowledge_import_operations` (S3) | Recipient ID, archive/version, fixed confirmed item set, state/timestamps/counts; one confirmed operation at a time per recipient. |
| `knowledge_import_items` (S3) | Unique `(org, archive ID, version, item ID, recipient permanent ID)`; durable intent, reserved target MEM ID/content attribution, final mapping or failure/uncertainty. Links to operations preserve prior-import skip outcomes. |

Per MEM-498, any necessary additive column is installed first using the existing schema migration pattern, then its index is created after the block; new-table indexes follow their table creation. Validate fresh and existing DB layouts and duplicate/collision constraints. S0 installs nothing; final schema/compatibility review remains a later gate.

Use the existing audit envelope `(task_id, agent, action, payload)` and real task/session lifecycle records; `AuditLogger` already delegates to `insert_audit_log` (`audit_logger.py:17`, `:29`). ### Exact item identity and reconciliation

Identity is `(org, archive ID, archive version, item ID, recipient permanent ID)`, never body similarity, title, filename or source MEM ID alone. Every successful item has a retrievable target MEM ID. Shared receipt uniqueness covers repeats and different confirmed selections; later archive versions do not silently update prior imports.

1. Persist the fixed operation and an item intent, including reserved target MEM ID and exact expected inherited content, before touching recipient files.
2. Revalidate admission and inspect existing receipts/intents. A completed mapping is skipped with its existing MEM ID; it is not written again.
3. Write the new note through the additive no-compaction path, read it back and confirm its identity/content/provenance, then durably commit the exact receipt/mapping. File and SQLite effects are not one atomic transaction: the intermediate intent is necessary.
4. If the response/receipt fails after a possible write, mark the item held for reconciliation. Inspect the original reserved MEM ID and exact attribution/content. A proven matching write can finalize its receipt; proven unwritten intent may resume. Missing, contradictory or unreadable evidence stays uncertain, with no fresh ID or blind second write.
5. A partial retry retains the original fixed selection and operation. Keep successes, return mappings for skips and write only confirmed missing/failed-unwritten items. A changed selection needs new confirmation and still respects global item identity. Never roll back by deleting successful notes.

Operations expose Queued / Processing / Succeeded / Partially failed / Failed, timestamps, pending counts and per-item results. At terminal accounting, `selected = imported + skipped + failed`; unattempted items count as failed with their cause. A possibly written item carries an explicit uncertainty-hold reason within the non-success outcome and is never advertised as safely retryable or known absent. During reconciliation it is not Succeeded. Succeeded requires durable mappings and no failed/pending/held item. Reload/lost response reopens the original receipt. Recipient detail persistently lists learned sources, archive versions/counts and receipt links.

Imports affect future retrieval through normal memory interfaces in a **fresh recipient session**; an already-running or resumed conversation is not rewritten. Retrieval is not a guarantee that every response recalls every item. No automatic KB promotion/publication or cross-archive semantic deduplication engine is added.
