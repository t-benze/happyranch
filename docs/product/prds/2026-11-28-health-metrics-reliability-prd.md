## Recommendation and user decisions

Make Health a trustworthy investigation starting point. The first release must expose failed starts and blocked progress, repair misleading history and labels, and reduce repeated dashboard storage without losing access to diagnostic records. Detailed resource analysis and new HTTP analytics should wait. This gives up breadth to answer three operator questions reliably:

1. Is work executing, waiting for something, or failing?
2. What was actually observed in the selected window, and what is unknown?
3. Which canonical record should I open to investigate or make a decision?

A reachable collector is evidence about the collector. A session heartbeat is evidence of liveness. Neither proves useful work is progressing. Health must preserve these distinctions and must never combine them into a universal green score.

At the inspected revision:

- `HealthPage.tsx` fixes `since` when the window is selected and passes no history limit. `useMetrics` polls every 15s; `useMetricsHistory` has no polling interval. Trends use an index-based Sparkline and compute maxima from returned points.
- `routes/metrics.py` defaults to 500 rows and permits at most 5,000. `metrics_store.py` takes daemon-global snapshots on scheduler ticks, throttled to at least 55s between writes, and retains 30 days. This is approximately minute sampling, not continuous incident accounting.
- `metrics.py` retains the last at most 1,024 latency samples per route and separately for all routes. Its count is retained samples; percentiles overlap across successive snapshots and reset with the registry.
- `host_session_store.py` keeps at most 64 receipts in memory. `published_total` is process-lifetime publications; `by_terminal_reason` and other receipt aggregates describe the retained deque, not all publications. Receipt summaries lack durable attempt identity and occurrence timestamps. Empty fallback shapes can resemble measured zeroes unless explicit availability is added.
- Supervisor admission already exposes active/cap/queue/oldest wait/head stall reason, backend capabilities and residue gates. A pre-start prepare/spawn failure can return without a receipt. `on_started` is a distinct boundary after launch/bind. Task native launch-refusal audits and session-start records are additional evidence, not automatically a complete common attempt ledger.
- Task and job headline gauges count loaded-org nonterminal tasks and a default-limited list of retained `running` job rows (the DB list defaults to 50). These do not establish execution or process liveness. The job detail route can explicitly return `job_liveness_unknown`. `run_step_worker` duration covers an entire queue run step, including awaited session work and finalization, and records completion with interval zero.

### Product interpretation and hypotheses

**Inference:** plausible cards and green connection copy can reassure the Founder while a launch has failed, work is queued, or data collection has stopped. Misleading time windows prevent reliable incident comparison. These are product risks grounded in E1–E3, not measured user-error rates.

**Hypothesis to validate:** compact aggregate snapshots could reduce new metrics payload growth by roughly 75% at comparable workload. This is an efficiency estimate from E1's payload mix. It is not the primary user outcome, a guaranteed saving or permission to reclaim existing DB space.

## Users and workflows

The primary user is the Founder operating a multi-org daemon and deciding whether to investigate failed work, handle a human decision, or ask Engineering to examine capacity or runtime behavior. A delegated operator uses the same evidence within existing access. Engineering investigates canonical task/session/job/audit records; QA verifies reconciliation. This PRD creates no new operator role or permissions.

| Workflow | Health must enable | Decision stays elsewhere |
| --- | --- | --- |
| A requested review does not start | Find a recorded pre-start failure/refusal, its attempt stage and time, and open its task and diagnostic evidence | Retry, recovery, cancellation and policy decisions remain on canonical authorized surfaces |
| Work is waiting | See active/capacity, queued demand, oldest wait and observed reason; distinguish human decision, dependency, provider/admission wait and parked parent | Capacity/provider changes and human approvals remain explicit decisions |
| Investigate the previous day/week | Select a rolling window, see actual coverage, event counts, sampled peaks, gaps and restart boundaries; open an incident's retained sources | No inferred root cause or automatic remediation |
| Page answers but collector stops | See connection reachable separately from stale historical collection and uncertain workload visibility | Investigate collection; do not conclude workloads are healthy or failed |
| Review an old running job | Distinguish positive current runner evidence from unknown retained status and follow the job detail | No automatic declaration of death, cleanup or job-state repair |

## Measurement contract

### Shared time, scope, freshness and coverage rules

All proposed values carry source identity/type, definition version, `as_of`, unit, scope, availability, and a coverage descriptor. Event projections additionally carry occurrence time and completeness/watermark; gauges carry collection time and sampling cadence; sample statistics carry their sample basis. Browser request success alone cannot refresh these timestamps.

- **Time:** store/compare aware instants in UTC. Render the user's timezone explicitly, with UTC in details. Calendar/DST offsets must not change a rolling elapsed-hour window. A history response pins server cutoff T and exact interval **[T−W, T)**. Bucket boundaries use the same half-open convention; no duplicated event on a boundary. Live cards state their own as-of, distinct from historical T.
- **Scope:** current metrics and supervisor are daemon-global across loaded orgs. Health appears beneath an org URL, so prominently say “Daemon · all loaded organizations.” Selecting another org must not silently relabel these values. Task/job diagnostic links preserve their actual org. Org-specific projections require genuine attribution; unknown-org evidence stays unattributed. A supervisor lease, tracked task session and running task are separate units and need not be equal.
- **Freshness proposal:** while visible, live reads every 15s and rolling history every 60s; refresh immediately on returning to a hidden tab or changing windows. Live collection is stale when age **>45s**; persisted collection stale when age **>180s**, based on the approximate 60s cadence. Equality remains fresh. A response received now with old source time remains stale. Display the actual age even below the threshold. These three-missed-cycle thresholds tolerate ordinary jitter; they do not assert outage or workload failure.
- **Coverage:** report requested bounds, earliest/latest valid observation, expected/observed sample slots, missing/invalid slots, widest gap, and event-accounting coverage separately for every source. For proposed 60s sampling, assign each sample to its UTC minute slot; numerator is occupied valid slots, denominator is slots intersecting the requested interval. This is **sample-slot coverage**, never uptime or incident-free coverage. Expose source-specific cadence for legacy rows; if not reconstructable, percentage is unavailable. Do not subtract downtime to inflate coverage. Warm-up, rollout start, eviction, reset and invalid data are explicit limitations.
- **States:** loading; available with measured zero; available with no events/zero traffic; empty history (no stored observations); partial; stale (retain last known with age); unavailable (collection/query failed); unsupported/unwired; denied; invalid/unknown. These are independent of workload states and can coexist (for example, a known failure plus partial coverage). An unavailable store/fallback must not serialize or render a convincing measured zero. A rate with denominator zero is “No resolved eligible launch outcomes,” never 0%; eligible attempts still pending are shown separately.

### Attempt accounting and reconciliation

The required feature is failure visibility, including failures with no terminal receipt. Engineering must prove whether existing canonical lifecycle/native launch records suffice for the following projection; the current receipt deque does not. Do not create a second task/session authority in a metrics store.

1. **Unit:** one actual native launch attempt, with stable org/producer invocation identity, daemon epoch, attempt identity/ordinal, stage timestamps, start evidence (known true/known false/unknown), terminal disposition/reason, and links to existing canonical records. Task/thread/dream/wake/schedule are separate producer kinds. If any kind cannot be joined completely, disclose its coverage and withhold an all-producer rate. A task may have multiple attempts; task impact is a separately labelled distinct-task count only where deduplicable.
2. **Eligibility:** a launch attempt becomes eligible immediately before the first native backend preparation operation for that attempt, after producer admission and required preflight have allowed execution. Instrument this actual seam once; a queue entry or allocated session ID is not an attempt. Preparation/spawn failure after this boundary is an eligible failed launch when no start is positively established. Prompt/permission/integrity/Pause/admission refusals before this seam remain visible as pre-start refusals, outside the rate. Do not infer eligibility from the eventual task status.
3. **Cohort:** proposed rate is a **resolved launch-outcome rate**, grouped by the time the launch outcome is known, not task creation or final task completion. For window [T−W,T), S is the count of unique eligible attempts whose authoritative started boundary first occurred in the window. F is eligible attempts whose known pre-start prepare/spawn/launch failure resolved in the window without a start. Once S is recorded, a later runtime failure does not add F. Include S+F as denominator and label “Failed launches / resolved eligible launch outcomes.” Attempts eligible earlier but resolved now are included; pending attempts remain separately visible. This prevents long sessions from delaying the denominator.
4. **Exclusions and uncertainty:** intentional pre-start cancellation/shutdown, policy refusal and provider deferral without native preparation are excluded and separately counted. Post-start cancellation counts in S and its cancellation outcome, never F. A failed preparation caused by a known provider error is F only if it crossed eligibility and meets stage evidence; no guessed provider cause. Unknown start/outcome/identity, lost publisher record, unsupported producer and ambiguous joins are disclosed; rate is unavailable if they prevent a complete eligible cohort. Zero S+F yields “No resolved eligible launch outcomes,” with any eligible pending attempts still shown separately. No partial rate extrapolation.
5. **Retries:** each genuine re-preparation/relaunch is a new attempt; correlation under the original invocation preserves retry history. A retry request or a callback-only recovery is not automatically a new eligible attempt. An internal supervisor 429 finish/release/re-admit/relaunch counts separately if it actually crosses the seam again. Do not sum overlapping snapshots, resent callbacks or duplicate receipt publications. Deduplication follows canonical identity, never timestamp proximity or a guessed task-name pattern.
6. **Receipts:** attach a receipt where it exists; retain primary terminal reason independently of cleanup result and publication status. Reconcile attempts → start/refusal/outcome → optional receipt at a pinned cutoff with explicit unmatched/duplicate counts. A failed launch without a receipt must remain visible; a receipt without a join remains “Unattributed receipt,” not silently dropped or assigned to a task. No record means unknown unless positive source completeness proves an empty population.
7. **Durability and event time:** account at lifecycle transitions, not minute polling. Persist/reconstruct sufficient bounded projection state under existing source access/retention; identify restarts and collector outages explicitly. Historical event counts are exact only for proven covered intervals. Late-arriving outcomes are placed by source occurrence time and may revise a displayed bucket with updated `as_of`; never duplicate them by receipt arrival time. If durable event instrumentation or new storage is necessary, D2/G2 must approve its bounded design before build. Uninstrumented history is partial/unavailable, never backfilled from the 64-item ring.

### Task state projection

The task breakdown is exclusive and reconciles to the included nonterminal record total at a pinned cutoff, with scope and excluded terminal rows stated. Use authoritative task type/ownership/control/wait markers; never `TASK-SEQ` name heuristics. Proposed classification precedence: internal carrier; otherwise positive current execution; otherwise parked parent with outstanding owned dependencies; otherwise explicit human wait; otherwise explicit dependency/job/provider/admission wait; otherwise eligible queued; otherwise unknown. If authoritative states conflict, use unknown with conflicting-source disclosure rather than forcing precedence. Preserve secondary wait reasons and existing lifecycle status in details. Parent and child are distinct records, but never summed and labelled independent running work. Liveness/last receipt alone does not measure substantive progress.

## Collection, aggregation and bounded cost

### Event accounting versus gauges

- Launch/refusal/start/terminal/retry/receipt publication are **events**. Count each identified event once in its time bucket; maintain source completeness and reason distributions. A failure that begins and ends between minute samples must still be counted if the lifecycle source covered it. No “zero failures” claim from gauges or a missing event collector.
- Admission demand, job/task state, session counts and queue depth are **gauges**. Proposed sampling remains approximately 60s, with live reads at 15s. Each historical bucket retains first/last timestamps and values, min, max, sample count, slot coverage and gaps; expose the **maximum observed sample**, not an asserted continuous maximum. For wait age, preserve observed maximum age and corresponding time/reason. Avoid retaining only averages or the last point, which erase useful pressure peaks.
- Historical HTTP data is a **snapshot of a rolling sample statistic**. If retained, label each point accordingly. Never average snapshot p95s into a window p95 or sum retained ring counts into traffic. v1 may remove the misleading HTTP trend and retain the truthful current table; adding interval histograms/real request counters is deferred.

### History representation

Proposed bounded resolutions are 1h in 1-minute buckets (60), 24h in 5-minute buckets (288), and 7d in 30-minute buckets (336), at most **400 buckets per series** including partial edge buckets. The axis remains the requested time interval even with empty edges. Server cutoff T and requested bounds are returned, not inferred from the first point. Bucket alignment is UTC; the chart uses actual instants and names display timezone.

Show a gauge max envelope plus last observation where useful; first/min/max/last values carry timestamps in inspection details. Event counts are sums of deduplicated events, not sampled maxima. Partial buckets disclose coverage. A missing/invalid slot remains missing inside a nonempty bucket; coarse bucketing must not conceal its span. Do not join a line across a collection gap greater than **180s** or a known restart. Smaller missing slots still contribute to missing coverage and tooltip gaps. Bound detailed gap/restart markers (proposed 200 of each); overflow shows exact total if known plus a “more gaps/restarts” summary and investigation range, never silent truncation or a fake continuous segment. Legacy inferred markers are labelled inferred. Data out of retention or before instrumentation began remains unavailable.

Rolling windows recompute T−W and T on each refresh; both cards and history show independent as-of times. A later response for an old selection must not overwrite the current window. Returning to a hidden tab refreshes first. An optional fixed incident interval must explicitly say it is fixed; a long-open “Last 24h” cannot become a fixed historical interval.

## UI information hierarchy and states

1. **Context strip:** “Daemon · all loaded organizations,” selected rolling window, timezone, transport state, live as-of and historical collection as-of/age. Show partial coverage or a collector warning before charts. No green “Live” health claim.
2. **Work requiring investigation:** failed launches, post-start failures/timeouts, pre-start refusals, unknown outcomes and cleanup/residue obstruction. Show separate counts by kind/reason, selected event window, exclusions/coverage and latest known evidence. Rate appears only under its proven contract. No incident text invents a cause. A known incident remains visible when another source becomes unavailable.
3. **Progress and waiting:** active leases/capacity, admission queue/oldest wait/head reason, task breakdown and job observed/unknown liveness. Present human waits and parked parents as states, not failures. Unknown reason says “Reason unavailable.” Show a source timestamp beside numeric age.
4. **Trends:** time axis over actual requested bounds, observed sample peaks/event counts, gap/restart markers and coverage inspector. Current cards must not be mistaken for values at historical cutoff.
5. **Supporting diagnostics:** loop late ticks, last run-step duration, backend capabilities, retained-receipt window, truthful HTTP sample table and existing diagnostic resource provenance. Progressive detail keeps failures/waits primary.

Every card supports source/window/scope/limitations details without requiring the user to interpret a metric field name. Loading has placeholders, never zero. Empty history says “No stored observations for this interval”; known complete event population with zero events says “No recorded failures in covered interval.” Zero eligible attempts and zero HTTP samples use their specific states. Stale keeps last known values with age; unavailable/denied offers an authorized retry or canonical navigation. No red failure status is inferred from unavailable data alone. Freshness, coverage and workload condition must be visible in text, not color only.

### Canonical diagnostic navigation

Use existing routes: `/orgs/:slug/tasks/:task_id`, `/orgs/:slug/jobs/:job_id`, thread/run detail where the record is actually linked, and `/orgs/:slug/audit` with supported action/time/source filters. Task native launch-boundary evidence also has the existing read-only `happyranch preparation-recovery TASK --org ORG --json` path when the browser cannot render it. Do not fabricate a receipt-detail URL: current receipt summaries lack stable identity/time. G2 must establish a safe association or a bounded authenticated diagnostic projection with a link back to retained owner records. If only a CLI investigation is possible, provide exact non-secret record identifiers and read-only command, with an explicit limitation; the controlled v1 incident cases still need a usable path within two navigation actions.

An expired, missing, denied or unattributed source says so and preserves the known count and evidence timestamp. No cross-org switch to the current URL's org, no anonymous access to private receipt/source detail, and no exposure of raw diagnostic bodies, survivor PID identities or probe exceptions on public `/health`. The existing unauthenticated liveness endpoint remains an independent minimal surface. Health offers navigation, not recovery/stop/retry/maintenance buttons.

Implement affected app-owned text in English and Simplified Chinese together under the existing web contract. Keyboard and screen-reader users must reach filters, sources, legends and gap/coverage details. State announcements must not steal focus; locale switching preserves selection/drafts/focus and triggers no extra requests or mutations. Proposed verification viewports are the repository's 390×844 and 1440×900.
