## Recommendation and user decisions

Make Health a trustworthy investigation starting point. The first release must expose failed starts and blocked progress, repair misleading history and labels, and reduce repeated dashboard storage without losing access to diagnostic records. Detailed resource analysis and new HTTP analytics should wait. This gives up breadth to answer three operator questions reliably:

1. Is work executing, waiting for something, or failing?
2. What was actually observed in the selected window, and what is unknown?
3. Which canonical record should I open to investigate or make a decision?

A reachable collector is evidence about the collector. A session heartbeat is evidence of liveness. Neither proves useful work is progressing. Health must preserve these distinctions and must never combine them into a universal green score.

### Product interpretation and hypotheses

**Inference:** plausible cards and green connection copy can reassure the Founder while a launch has failed, work is queued, or data collection has stopped. Misleading time windows prevent reliable incident comparison. These are product risks grounded in E1–E3, not measured user-error rates.

**Hypothesis to validate:** compact aggregate snapshots could reduce new metrics payload growth by roughly 75% at comparable workload. This is an efficiency estimate from E1's payload mix. It is not the primary user outcome, a guaranteed saving or permission to reclaim existing DB space.

## Measurement contract

### Shared time, scope, freshness and coverage rules

All proposed values carry source identity/type, definition version, `as_of`, unit, scope, availability, and a coverage descriptor. Event projections additionally carry occurrence time and completeness/watermark; gauges carry collection time and sampling cadence; sample statistics carry their sample basis. Browser request success alone cannot refresh these timestamps.

- **Time:** store/compare aware instants in UTC. Render the user's timezone explicitly, with UTC in details. Calendar/DST offsets must not change a rolling elapsed-hour window. A history response pins server cutoff T and exact interval **[T−W, T)**. Bucket boundaries use the same half-open convention; no duplicated event on a boundary. Live cards state their own as-of, distinct from historical T.
- **Scope:** current metrics and supervisor are daemon-global across loaded orgs. Health appears beneath an org URL, so prominently say “Daemon · all loaded organizations.” Selecting another org must not silently relabel these values. Task/job diagnostic links preserve their actual org. Org-specific projections require genuine attribution; unknown-org evidence stays unattributed. A supervisor lease, tracked task session and running task are separate units and need not be equal.
- **Freshness proposal:** while visible, live reads every 15s and rolling history every 60s; refresh immediately on returning to a hidden tab or changing windows. Live collection is stale when age **>45s**; persisted collection stale when age **>180s**, based on the approximate 60s cadence. Equality remains fresh. A response received now with old source time remains stale. Display the actual age even below the threshold. These three-missed-cycle thresholds tolerate ordinary jitter; they do not assert outage or workload failure.
- **Coverage:** report requested bounds, earliest/latest valid observation, expected/observed sample slots, missing/invalid slots, widest gap, and event-accounting coverage separately for every source. For proposed 60s sampling, assign each sample to its UTC minute slot; show occupied valid slots and expected slots intersecting the requested interval as counts. This is **sample-slot coverage**, never uptime or incident-free coverage. Expose source-specific cadence for legacy rows; if not reconstructable, coverage is unknown. Do not add a coverage-percentage widget. Do not subtract downtime to inflate coverage. Warm-up, rollout start, eviction, reset and invalid data are explicit limitations.
- **States:** loading; available with measured zero; available with no events/zero traffic; empty history (no stored observations); partial; stale (retain last known with age); unavailable (collection/query failed); unsupported/unwired; denied; invalid/unknown. These are independent of workload states and can coexist (for example, a known failure plus partial coverage). An unavailable store/fallback must not serialize or render a convincing measured zero. Unresolved attempts remain visible separately, including when there are no known failures. Omit rate-related placeholders entirely.

### Attempt accounting and reconciliation

The required feature is failure visibility, including failures with no terminal receipt. Founder seq32 selected attempt recording; failure-only recording is not the release contract. Existing receipt memory cannot provide complete identity/stage coverage. Do not create a second task/session authority in a metrics store.

1. **Unit and seam:** one actual native launch attempt with stable org/producer invocation identity, daemon epoch, attempt ID/ordinal, occurrence timestamps, positive start evidence (known true/known false/unknown), disposition/reason and canonical source links. Cover task/thread/dream/wake/schedule. Record eligibility once immediately before actual backend preparation, after producer admission/preflight. Queue entries and reserved session IDs are not attempts. Pre-seam policy/Pause/integrity/admission refusals remain separately visible, without inventing an attempted launch.
2. **Forward-only lifecycle recording:** Engineering proposes a new append-only audit action at the shared supervisor seam: attempted/eligible, then positively started or known pre-start failure. Existing fixed-shape native-boundary and producer lifecycle actions keep their meanings. A DB sink, scope mapping, fields, bounded read design and launch-path review remain Engineering design dependencies. Reuse existing audit retention/access; no migration is authorized by this document. Recording begins at rollout; never reconstruct absent events from notes or the receipt ring.
3. **Reconciliation, not a percentage:** at pinned cutoff T, reconcile recorded attempts → positive start or pre-start failure → post-start outcome → optional receipt. Show recorded attempts, known failed launches, failures after starting, intentional refusal/cancellation and unresolved/missing/duplicate/unattributed evidence separately. Attempts with no recorded outcome remain unresolved, never implicit success. Post-start failure never becomes a failed launch. Exact counts reconcile to the covered source population, with known failures placed by outcome occurrence time in [T−W,T). Details show attempt/start times and links for cross-window joins; an unresolved carry-over remains visible with its original time. No denominator calculation or rate eligibility/unlock is a release requirement.
4. **Retries and uncertainty:** a genuine new preparation/relaunch gets a new attempt ID linked to its original invocation, including a supervisor re-admission that actually crosses the seam again. Callback recovery, duplicate delivery and retry requests alone are not new attempts. Keep pre/post-start cancellation distinct. Ambiguous stage, unsupported producer, missing join, failed write and missing publication reduce stated coverage; never infer a root cause or assign a record by timestamp proximity.
5. **Receipts and durability:** receipts are optional evidence, not the accounting source. Preserve primary outcome separately from cleanup and publication status. An unmatched receipt remains unattributed; missing receipt does not erase a known failure. Covered event counts must survive >64 receipts and projection/daemon restart under existing source retention, or explicitly disclose lost continuity. Late events update their source-time bucket once. Source completeness for older intervals remains partial/unknown.
6. **Collection-failure boundary:** recording must not block or change launch outcomes. Engineering must validate failure/skip signals, independent coverage reporting, crash windows and missing first-write behavior. An attempt record helps expose missing outcomes but cannot prove perfect producer coverage or that no first attempt write was lost. Zero means no known failures within explicitly stated coverage, not universal success. No historical backfill, automatic rate, remediation or retention expansion follows.

### Task state projection

The task breakdown is exclusive and reconciles to the included nonterminal record total at a pinned cutoff, with scope and excluded terminal rows stated. Use authoritative task type/ownership/control/wait markers; never `TASK-SEQ` name heuristics. Proposed classification precedence: internal carrier; otherwise positive current execution; otherwise parked parent with outstanding owned dependencies; otherwise explicit human wait; otherwise explicit dependency/job/provider/admission wait; otherwise eligible queued; otherwise unknown. If authoritative states conflict, use unknown with conflicting-source disclosure rather than forcing precedence. Preserve secondary wait reasons and existing lifecycle status in details. Parent and child are distinct records, but never summed and labelled independent running work. Liveness/last receipt alone does not measure substantive progress.

## Collection, aggregation and bounded cost

### Event accounting versus gauges

- Launch/refusal/start/terminal/retry/receipt publication are **events**. Count each identified event once in its time bucket; maintain source completeness and reason distributions. A failure that begins and ends between minute samples must still be counted if the lifecycle source covered it. No “zero failures” claim from gauges or a missing event collector.
- Admission demand, job/task state, session counts and queue depth are **gauges**. Proposed sampling remains approximately 60s, with live reads at 15s. Each historical bucket retains first/last timestamps and values, min, max, sample count, slot coverage and gaps; expose the **maximum observed sample**, not an asserted continuous maximum. For wait age, preserve observed maximum age and corresponding time/reason. Avoid retaining only averages or the last point, which erase useful pressure peaks.
- Historical HTTP data is a **snapshot of a rolling sample statistic**. If retained, label each point accordingly. Never average snapshot p95s into a window p95 or sum retained ring counts into traffic. Product recommends removing the misleading HTTP p95 history chart and retaining the truthful current table (design7, Founder pending); adding interval histograms/real request counters is deferred.

### History representation

Proposed bounded resolutions are 1h in 1-minute buckets (60), 24h in 5-minute buckets (288), and 7d in 30-minute buckets (336), at most **400 buckets per series** including partial edge buckets. The axis remains the requested time interval even with empty edges. Server cutoff T and requested bounds are returned, not inferred from the first point. Bucket alignment is UTC; the chart uses actual instants and names display timezone.

Show a gauge max envelope plus last observation where useful; first/min/max/last values carry timestamps in inspection details. Event counts are sums of deduplicated events, not sampled maxima. Partial buckets disclose coverage. A missing/invalid slot remains missing inside a nonempty bucket; coarse bucketing must not conceal its span. Do not join a line across a collection gap greater than **180s** or a known restart. Smaller missing slots still contribute to missing coverage and tooltip gaps. Bound detailed gap/restart markers (proposed 200 of each); overflow shows exact total if known plus a “more gaps/restarts” summary and investigation range, never silent truncation or a fake continuous segment. Legacy inferred markers are labelled inferred. Data out of retention or before instrumentation began remains unavailable.

Rolling windows recompute T−W and T on each refresh; both cards and history show independent as-of times. A later response for an old selection must not overwrite the current window. Returning to a hidden tab refreshes first. An optional fixed incident interval must explicitly say it is fixed; a long-open “Last 24h” cannot become a fixed historical interval.

## UI information hierarchy and states

1. **Context strip:** “Daemon · all loaded organizations,” selected rolling window, timezone, transport state, live as-of and historical collection as-of/age. Show partial coverage or a collector warning before charts. No green “Live” health claim.
2. **Work requiring investigation:** failed launches, post-start failures/timeouts, pre-start refusals, unknown outcomes and cleanup/residue obstruction. Show separate counts by kind/reason, selected event window, exclusions/coverage and latest known evidence. No rate line, placeholder or complete-data toggle appears in production. No incident text invents a cause. A known incident remains visible when another source becomes unavailable.
3. **Progress and waiting:** active leases/capacity, admission queue/oldest wait/head reason, task breakdown and job observed/unknown liveness. Present human waits and parked parents as states, not failures. Unknown reason says “Reason unavailable.” Show a source timestamp beside numeric age.
4. **Trends:** time axis over actual requested bounds, observed sample peaks/event counts, gap/restart markers and coverage inspector. Current cards must not be mistaken for values at historical cutoff.
5. **Supporting diagnostics:** loop late ticks, last run-step duration, backend capabilities, retained-receipt window, truthful HTTP sample table and existing diagnostic resource provenance. Progressive detail keeps failures/waits primary.

Every card supports source/window/scope/limitations details without requiring the user to interpret a metric field name. Loading has placeholders, never zero. Empty history says “No stored observations for this interval”; known complete event population with zero events says “No recorded failures in covered interval.” Zero recorded attempts is shown with source coverage; unresolved attempts stay visible. Zero HTTP samples uses its specific state. Stale keeps last known values with age; unavailable/denied offers an authorized retry or canonical navigation. No red failure status is inferred from unavailable data alone. Freshness, coverage and workload condition must be visible in text, not color only.
